    06 - SMB & Permissions

    Goal

    In this lesson, you will create a shared folder on Windows Server and use Active Directory Security Groups to control who can access it.

    By the end of the lesson, you should understand:

    • what SMB is
    • what a network share is
    • the difference between Share and NTFS permissions
    • how Active Directory groups can control resource access
    • how authentication and authorization appear in a real access test
    • why permissions should normally be assigned to groups rather than individual users
    • how to troubleshoot an Access Denied error

    Where We Are

    Our environment now contains:

    Active Directory
      │
      ├── Users
      │
      └── Security Groups
              │
              ├── GG-Nurses
              ├── GG-Doctors
              ├── GG-Pharmacy
              └── GG-IT

    The groups exist, but they do not yet control a real resource.

    In this lesson, we will connect a Security Group to a shared folder.

    For example:

    Emma Wilson
     │
     └── GG-Nurses
              │
              ▼
       Clinical Share
              │
              ▼
         Access Granted

    while another authenticated user may receive:

    Marie DelGloria
       │
       └── Not a member of GG-Nurses
                    │
                    ▼
              Clinical Share
                    │
                    ▼
               Access Denied

    This turns our IAM model into a real authorization test.

    What Is SMB?

    SMB stands for Server Message Block.

    It is a network protocol commonly used by Windows systems to provide access to resources such as:

    • shared folders
    • files
    • printers

    A simplified SMB connection looks like:

    Client Computer
      │
      │ SMB
      │ TCP 445
      ▼
Windows Server
      │
      └── Shared Folder

    The modern SMB service normally uses:

    TCP 445

    What Is a Network Share?

    A folder normally exists on one computer.

    For example:

    C:\HospitalData\Clinical

    A network share makes that folder available to authorized systems over the network.

    It might be accessed using a UNC path such as:

    \\DC01\Clinical

    or:

    \\<server-ip>\Clinical

    What Is a UNC Path?

    UNC stands for Universal Naming Convention.

    A UNC path identifies a network resource.

    The general format is:

    \\ServerName\ShareName

    For example:

    \\DC01\Clinical

    The first component identifies the server.

    The second identifies the shared resource.

    Our Access Model

    For this lesson, imagine that the hospital has a shared clinical folder intended for nursing staff.

    We want:

    GG-Nurses
    │
    ▼
Clinical Share
    │
    └── Access

    The important point is that we do not assign the permission directly to Emma.

    Instead:

    Emma
  ↓
GG-Nurses
  ↓
Permission
  ↓
Clinical Share

    This makes access easier to manage.

    Before You Start

    Confirm that:

    • Active Directory is running
    • the Security Groups exist
    • at least one test user belongs to GG-Nurses
    • another test user exists outside GG-Nurses
    • Windows Server networking is working

    You can verify the Nurses group with:

    Get-ADGroup -Identity GG-Nurses

    To inspect its members:

    Get-ADGroupMember -Identity GG-Nurses

    Step 1 - Create the Folder

    On Windows Server, create a folder for the simulated resource.

    For example:

    C:\HospitalData\Clinical

    You can create it through File Explorer.

    Or with PowerShell:

    New-Item -Path "C:\HospitalData\Clinical" -ItemType Directory

    Step 2 - Add a Test File

    Inside the folder, create a harmless test file.

    For example:

    welcome.txt

    The file might contain:

    This is a simulated clinical resource.
No real patient information is stored here.

    Warning

    Never place real patient data, workplace information, passwords or production credentials inside this learning environment.

    Step 3 - Share the Folder

    Right-click the Clinical folder.

    Open:

    Properties → Sharing

    Then choose:

    Advanced Sharing

    Enable:

    Share this folder

    Use a simple share name such as:

    Clinical

    The network path will eventually resemble:

    \\DC01\Clinical

    Your server name may be different.

    Step 4 - Understand Share Permissions

    A Windows file share can have Share Permissions.

    Examples include:

    • Read
    • Change
    • Full Control

    Share permissions apply when the resource is accessed through SMB over the network.

    For example:

    Client
   │
   │ SMB
   ▼
Share Permissions
   │
   ▼
Shared Folder

    Step 5 - Understand NTFS Permissions

    The folder also exists on an NTFS filesystem.

    NTFS permissions can control actions such as:

    • Read
    • Write
    • Modify
    • Full Control

    These permissions apply to the files and folders themselves.

    So Windows may evaluate two permission layers when a user accesses the folder through the network:

    User
 ↓
SMB Share Permission
 ↓
NTFS Permission
 ↓
Resource

    Share vs NTFS Permissions

    This distinction is important.

    Share Permissions

    Apply to access through the network share.

    NTFS Permissions

    Apply to the actual filesystem object.

    When both apply, the user does not gain more access simply because one layer is permissive.

    The effective access must satisfy the restrictions imposed by the relevant permission layers.

    For example:

    Share:
Read + Change

NTFS:
Read only

Result:
User cannot modify the file

    This is why both layers should be checked during troubleshooting.

    Step 6 - Assign Access to the Security Group

    Instead of assigning access directly to Emma Wilson, assign it to:

    GG-Nurses

    For a learning environment, you might allow the group to:

    Read
or
Modify

    depending on the scenario you want to test.

    The design should remain:

    Resource
   ↑
Permission
   ↑
GG-Nurses
   ↑
Users

    Why Not Assign the Permission Directly to Emma?

    This would technically work:

    Clinical
   ↑
Emma Wilson

    But imagine 200 nurses.

    You would eventually have:

    Clinical
   ├── Emma
   ├── Sarah
   ├── James
   ├── Anna
   ├── John
   └── ...

    That becomes difficult to maintain.

    A group model is cleaner:

    Clinical
   ↑
GG-Nurses
   ↑
200 nurses

    When someone joins the nursing team, you update their group membership.

    You do not need to redesign the resource permissions.

    Step 7 - Review NTFS Security

    Open:

    Clinical → Properties → Security

    Review the identities currently listed.

    Depending on your environment, inherited entries may already exist.

    Do not remove system or administrative permissions without understanding why they exist.

    Add:

    GG-Nurses

    and assign the level of access required for the exercise.

    For example:

    Read & execute
List folder contents
Read

    or, if the exercise requires users to modify files:

    Modify

    Least Privilege Still Applies

    Do not automatically grant:

    Full Control

    just because it is convenient.

    Ask:

    What does this group actually need to do?

    If nurses only need to read the resource:

    GG-Nurses
     ↓
Read

    may be more appropriate than:

    GG-Nurses
     ↓
Full Control

    This is the Principle of Least Privilege applied to files.

    Step 8 - Verify the Share

    Open PowerShell.

    Run:

    Get-SmbShare

    You should see the new share.

    For more information:

    Get-SmbShare -Name Clinical

    You can inspect share permissions with:

    Get-SmbShareAccess -Name Clinical

    Step 9 - Check That SMB Is Listening

    SMB normally uses TCP port 445.

    From another Windows system, you can test whether the server accepts connections to that port with:

    Test-NetConnection <server-ip> -Port 445

    A successful result may include:

    TcpTestSucceeded : True

    This tells you that the SMB service can be reached at the network layer.

    It does not prove that the user is authorized to the folder.

    Connectivity vs Authorization

    These are separate questions.

    Connectivity

    Can the client reach the SMB service?

    Client
  ↓
TCP 445
  ↓
Server

    Authentication

    Can the server verify the user's identity?

    Credentials
    ↓
Active Directory
    ↓
Authenticated

    Authorization

    Is that authenticated user allowed to access this share?

    Authenticated User
       ↓
Group Membership
       ↓
Permissions
       ↓
Granted / Denied

    This separation is essential during troubleshooting.

    Step 10 - Test an Authorized User

    Use a test user who belongs to:

    GG-Nurses

    For example:

    Emma Wilson

    From a Windows client or appropriate test session, access:

    \\DC01\Clinical

    or use the actual server name in your environment.

    If Emma:

    1. authenticates successfully
    2. belongs to GG-Nurses
    3. and GG-Nurses has the required permissions

    the expected result is:

    Access Granted

    Step 11 - Test an Unauthorized User

    Now use an account that is not a member of GG-Nurses.

    For example:

    Marie DelGloria

    Assume:

    Account exists
Password is valid
Account is enabled

    Marie may successfully authenticate.

    But when she attempts:

    \\DC01\Clinical

    the expected result is:

    Access Denied

    if no other permission grants her access.

    Why This Test Matters

    Compare the two users:

    Emma
 ├── Account valid
 ├── Authentication successful
 └── GG-Nurses member
           ↓
      Access Granted


Marie
 ├── Account valid
 ├── Authentication successful
 └── Not in GG-Nurses
           ↓
       Access Denied

    The difference is not identity verification.

    The difference is authorization.

    Authentication Success Does Not Mean Access Success

    This is a common troubleshooting mistake.

    Imagine a user says:

    My password works, but I cannot open the folder.

    Resetting the password may not solve anything.

    The identity may already be authenticated.

    The actual problem may be:

    • missing group membership
    • incorrect NTFS permissions
    • incorrect share permissions
    • access token not refreshed
    • wrong resource path

    Step 12 - Verify Group Membership

    Check whether the user belongs to the required group:

    Get-ADPrincipalGroupMembership emma.wilson

    Or inspect the group:

    Get-ADGroupMember GG-Nurses

    You should be able to determine whether the authorization relationship exists:

    Emma
  ↓
GG-Nurses

    Step 13 - Test a Permission Change

    For a controlled learning exercise, remove a test user from GG-Nurses.

    For example:

    Remove-ADGroupMember -Identity GG-Nurses -Members emma.wilson

    PowerShell will normally ask you to confirm the change.

    After the user's authentication context has been refreshed appropriately, test access again.

    The expected relationship becomes:

    Emma
  │
  └── No GG-Nurses membership
             ↓
        Clinical Share
             ↓
         Access Denied

    You can then restore the membership:

    Add-ADGroupMember -Identity GG-Nurses -Members emma.wilson

    This demonstrates that access comes from group membership rather than from Emma's identity being manually attached to the folder.

    Why Access Changes May Not Appear Immediately

    When users authenticate, Windows creates an access token containing information such as Security Group memberships.

    If a group membership changes while the user is already signed in, the current session may still contain the previous information.

    A new sign-in session may therefore be required before some permission changes are reflected.

    This is another reason troubleshooting should include the user's current authentication session.

    Step 14 - Inspect Current SMB Connections

    On the server, you can inspect SMB sessions using:

    Get-SmbSession

    You can also inspect files currently opened through SMB:

    Get-SmbOpenFile

    These commands can help determine whether clients are actually connected to the server.

    Troubleshooting Scenario 1

    The user reports:

    I cannot open \\DC01\Clinical.

    Start with the path.

    Check:

    Is the server name correct?
        ↓
Is the share name correct?
        ↓
Does the share exist?

    Verify:

    Get-SmbShare -Name Clinical

    Troubleshooting Scenario 2

    The server name cannot be resolved.

    Test DNS:

    nslookup DC01

    If name resolution fails, try to determine whether the issue is DNS rather than SMB.

    You can also temporarily compare behavior using the server IP:

    \\<server-ip>\Clinical

    If IP-based access behaves differently from name-based access, DNS deserves investigation.

    Troubleshooting Scenario 3

    The server is reachable but SMB is not.

    Test port 445:

    Test-NetConnection <server-ip> -Port 445

    If:

    TcpTestSucceeded : False

    investigate areas such as:

    • Windows Firewall
    • SMB service availability
    • network configuration
    • routing
    • wrong IP address

    Do not start changing Active Directory groups when the SMB service itself cannot be reached.

    Troubleshooting Scenario 4

    TCP 445 works but the user receives Access Denied.

    Now investigate authorization.

    Check:

    Get-ADPrincipalGroupMembership <username>

    Then:

    Get-SmbShareAccess -Name Clinical

    Also inspect:

    Folder Properties → Security

    because NTFS permissions may be responsible for the denial.

    A Layered Troubleshooting Model

    When an SMB resource cannot be accessed, work through the layers.

    1. Resource Path
       ↓
2. DNS / Server Resolution
       ↓
3. Network Reachability
       ↓
4. TCP 445
       ↓
5. Authentication
       ↓
6. Security Group Membership
       ↓
7. Share Permissions
       ↓
8. NTFS Permissions
       ↓
9. Effective Access

    This approach is much more useful than randomly changing permissions.

    Don't “Fix” Access by Granting Everyone Permission

    Suppose Marie receives Access Denied.

    A poor solution would be:

    Everyone
   ↓
Full Control

    The error disappears, but the security problem becomes much worse.

    The correct question is:

    Should Marie have access to this resource?

    If the answer is no:

    Access Denied

    is actually the correct system behavior.

    Not every error reported by a user represents a broken system.

    Access Denied Can Be a Successful Security Control

    This is an important IAM idea.

    If:

    Marie
   ↓
Not authorized
   ↓
Access Denied

    then the access-control system may be functioning exactly as intended.

    Troubleshooting therefore requires understanding both:

    • the technical behavior
    • the intended access policy

    SMB and Active Directory Together

    We can now see multiple technologies working together:

    User
 │
 ▼
Active Directory
 │
 ├── Authentication
 │
 └── Group Membership
          │
          ▼
     SMB Resource
          │
          ├── Share Permissions
          └── NTFS Permissions
                   │
                   ▼
            Access Decision

    This is much closer to how identity integration works in a real enterprise environment.

    What You Should Understand

    Before continuing, make sure you can explain:

    What is SMB?

    A network protocol commonly used to access shared files and other resources.

    Which port does modern SMB normally use?

    TCP 445.

    What is a UNC path?

    A network path such as:

    \\ServerName\ShareName

    Why use a Security Group instead of assigning permissions directly to every user?

    Because group-based permissions are easier to manage, review and scale.

    What is the difference between Share and NTFS permissions?

    Share permissions control network access through the share, while NTFS permissions control access to the filesystem object.

    Can a user authenticate successfully and still receive Access Denied?

    Yes.

    Authentication verifies identity.

    Authorization determines access.

    Is Access Denied always an error?

    No.

    If the user should not have access, the denial is the correct security outcome.

    Checkpoint

    Before moving on, confirm that:

    • a shared folder exists
    • the folder has an SMB share name
    • Get-SmbShare shows the share
    • a Security Group is used for access
    • NTFS permissions have been reviewed
    • share permissions have been reviewed
    • an authorized user can be tested
    • an unauthorized user can be tested
    • you understand authentication vs authorization
    • you understand why TCP 445 testing is different from permission testing

    Challenge

    Consider this scenario:

    Test-NetConnection DC01 -Port 445

TcpTestSucceeded : True

    Emma can access:

    \\DC01\Clinical

    Marie receives:

    Access Denied

    Both accounts have valid passwords.

    Answer:

    1. Is the network path to SMB working?
    2. Is TCP 445 available?
    3. Is Marie's password necessarily the problem?
    4. Which IAM information should you inspect?
    5. Should you simply add Marie to GG-Nurses?

    The answer to question 5 is:

    Only if her role genuinely requires nursing access.

    Authorization should follow business requirements, not simply remove error messages.
